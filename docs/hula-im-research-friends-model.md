# HuLa IM 研究好友模型

本文定义 `HuLa IM + Codex + CodexMonitor` 的产品语义和服务分层，用于解释“共同好友”“研究好友”“中心化持续研究”之间的关系。

## 背景

在 `HuLa IM` 中，用户天然习惯于：

- 添加好友
- 发起会话
- 在同一个联系人下持续沟通

这套交互语义很适合承载 AI 助手，但如果直接把所有能力都暴露成技术概念，例如 `agent`、`thread`、`workspace`，用户理解成本会偏高。

因此更合适的产品表达是：

- `Codex` 作为共同好友
- `CodexMonitor` 作为中心化转发和调度层
- 不同好友代表不同方向的研究能力

这样用户看到的是“联系人”和“会话”，系统内部运行的是“服务路由”和“任务线程”。

## 核心定义

### 1. Codex 是共同好友

`Codex` 是统一入口，承担三类职责：

- 接住用户的自然语言请求
- 理解用户想调用哪一类研究能力
- 把请求交给后端合适的研究好友或执行链路

在产品感知上，用户是在和一个共同好友聊天。

在系统语义上，`Codex` 是统一会话入口和能力编排入口。

### 2. CodexMonitor 是服务转发层

`CodexMonitor` 不直接强调“好友”语义，而是承担中心化基础设施职责：

- 管理服务端项目环境
- 管理 workspace、thread、task 和事件流
- 将消息路由到具体研究好友
- 汇总结果后回传给 `HuLa IM`
- 持续沉淀历史上下文、研究记录和执行状态

因此，`CodexMonitor` 更接近“研究调度中心”或“服务中台”，而不是单纯的桌面客户端。

### 3. 不同好友 = 不同研究方向

在 `HuLa IM` 里新增一个好友，产品上可以解释为：

- 新增一个专业研究助手
- 新增一个明确能力域
- 新增一个长期可复用的研究入口

例如：

- 市场研究好友
- 产品方案好友
- 代码审查好友
- 数据分析好友
- 运维排障好友

因此，“添加不同好友”本质上不是加联系人，而是给系统挂载不同的研究能力。

## 为什么要中心化

这个模型成立的前提，是后端采用中心化架构，而不是把能力散落在多个终端上。

中心化的价值主要有五点：

1. 研究可以持续积累，而不是随设备切换丢失。
2. 项目环境、依赖、权限、模型配置可以统一维护。
3. 不同客户端只负责接入，不负责承载核心执行环境。
4. 同一研究方向可以形成长期上下文和历史记忆。
5. 后续更容易支持多人协作、审计和治理。

换句话说，正因为系统是中心化的，研究这件事才有“持续支持”的基础。

## 产品语义与系统语义的映射

| 产品语义 | 系统语义 |
| --- | --- |
| 共同好友 `Codex` | 统一入口 / 能力编排层 |
| 研究好友 | 一个专业 agent 或一组同类能力 |
| 添加好友 | 接入一个新的研究能力模块 |
| 聊天会话 | 一个长期入口下的 thread 集合 |
| 一次提问 | 一个 task 或一次 thread turn |
| 继续追问 | 在同一 thread 中追加上下文 |
| 后台持续研究 | 服务端异步任务执行与状态跟踪 |

建议始终保持这个原则：

- 对用户讲“好友”和“会话”
- 对系统讲“agent”“thread”“task”和“route”

## 推荐工作链路

完整链路建议如下：

`用户 -> HuLa IM 会话 -> Codex -> CodexMonitor -> 研究好友 -> 结果回传到会话`

展开后可以理解为：

1. 用户在 `HuLa IM` 中给某个好友发送消息。
2. 如果该好友是统一入口 `Codex`，则由 `Codex` 判断该请求应转发给哪个研究方向。
3. `CodexMonitor` 根据能力映射、workspace 和 thread 状态执行路由。
4. 对应研究好友在服务端完成分析、生成、查询或执行。
5. 结果回写到原始 IM 会话。
6. 历史记录、事件、上下文和状态保存在中心服务端。

## 研究好友的两种组织方式

### 方式一：显式好友

每个研究方向都是一个独立好友。

优点：

- 用户理解直观
- 好友边界清晰
- 适合强专业分工场景

缺点：

- 好友数量变多后，联系人列表会膨胀

### 方式二：Codex 统一入口

用户主要添加一个 `Codex`，由 `Codex` 在内部选择研究好友。

优点：

- 用户入口统一
- 更适合逐步扩展能力
- 前端交互更简单

缺点：

- 用户对内部具体能力的感知会更弱

更稳妥的方案是混合模式：

- `Codex` 作为总入口
- 关键研究方向保留为可单独添加的专业好友

## 持续研究的关键能力

如果要把“好友”真正做成“长期研究助手”，需要在 `CodexMonitor` 侧补齐这些能力：

- 长期 thread 历史沉淀
- 按好友隔离的上下文记忆
- 可追踪的 task 状态
- 统一的消息路由与事件推送
- workspace 与执行环境绑定
- 鉴权、审计与权限治理

这部分能力决定了系统不是一次性聊天工具，而是可持续运行的研究平台。

## 对外表达建议

可以使用下面这段作为统一描述：

`在 HuLa IM 中，Codex 是统一入口，像一个共同好友；CodexMonitor 负责消息转发、任务调度和中心化研究沉淀；不同的智能好友对应不同领域的研究能力。用户每添加一个好友，本质上就是为系统接入一个新的专业研究助手。由于后端采用中心化架构，这些研究能力可以持续运行、持续积累，并在不同设备之间保持一致。`

## 实施建议

第一阶段建议先落地以下模型：

1. 保留 `Codex` 作为统一入口。
2. 在 `CodexMonitor` 中维护“好友 -> 能力 -> workspace/agent”映射。
3. 每个研究好友内部仍使用多 `thread` 承载具体任务。
4. 先做中心化消息路由和任务状态回传。
5. 后续再扩展权限、通知、多人共享和运营能力。

这样可以在不破坏现有 `thread/task/workspace` 结构的前提下，把产品抽象升级为“HuLa IM 中的研究好友体系”。
